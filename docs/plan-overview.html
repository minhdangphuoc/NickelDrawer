Kobo Libra 2 · firmware 4.38.23828 · native Nickel mod

Ngăn Ứng Dụng

A native app drawer built into the Kobo's own interface. Tools open as real Kobo screens with the same header, fonts, toggles and keyboard as Settings. A shared UI kit lets anyone build a new tool by describing its screen in a small JSON file, without writing C++.

Status: plan v2, native route chosen Effort: about 5–7 weeks in phases Already on device: Vietnamese UI mod, En–Vi dictionary, LocalSend receiver
Vision

Tools that feel like Kobo made them

The Libra 2 is a small, slow e-ink screen, so a browser page will always feel foreign there. The drawer will draw with the same Qt widgets and stylesheet Nickel (Kobo's reading app) already uses. Your eye can't tell a tool from a Kobo settings page, and dark mode and font size follow the system.

Native, not lookalike

The drawer runs inside Nickel and uses its widgets, stylesheet and on-screen keyboard. Screens get e-ink refresh handling for free.

UI kit, not C++ per app

One native mod renders every tool. A tool ships a ui.json screen plus any script or binary. Developers never touch libnickel.

Fails soft

If a firmware update changes Kobo internals, the drawer turns itself off and every tool stays reachable from the plain NickelMenu list.

One folder = one app

Copy a folder into .adds/apps/ to install, delete it to uninstall. The same folder works in the drawer and in the menu fallback.

How it fits together

One native host, many small tools

A single mod, libkoboapps.so, loads into Nickel at startup using NickelHook, the same framework NickelMenu and NickelClock use. It adds the drawer and renders each tool's screen with the UI kit. Tools do their work in a separate process and talk to the host with one JSON message per line. A crashing tool therefore can't take Nickel down.

Wireframes

What you will see on the Kobo

Drawn at the Libra 2's 1264 × 1680 proportions with example data. Every screen uses Nickel's own header with a back chevron, its list rows and its toggles. Nothing opens in a browser.

For developers

A tool is two JSON files and a program

The screen is declared in ui.json. The backend is any program that reads and writes one JSON object per line on stdin/stdout. It can be a shell script, Go or Python if the developer ships it. The host only runs actions listed in app.json.

// ui.json: LocalSend main screen
{
  "title": "LocalSend",
  "badge": "$status",
  "body": [
    { "text": "Mở LocalSend trên điện thoại…" },
    { "bigcode": "$pin" },
    { "kv": [["Tên máy", "$alias"],
              ["IP", "$ip"]] },
    { "toggle": "Tự cập nhật thư viện",
      "bind": "auto_rescan" },
    { "list": "$received", "title": "Đã nhận" },
    { "button": "Dừng nhận", "action": "stop",
      "style": "primary" }
  ]
}

Reverse engineering

Mapping libnickel with Ghidra

Nickel is closed source, but libnickel.so exports readable C++ and Qt symbols. Ghidra lets us list classes, read decompiled functions and trace how Kobo builds a settings screen.

  1. Get libnickel for 4.38.23828

    Extract it from the official firmware package on the Mac, matching the version on your Kobo. The Kobo binary never goes into our repo or any shared file.

  2. Load it into Ghidra

    Install Ghidra with JDK 21, then import and analyse the binary headless. One-time setup on your Mac.

  3. Find the pieces the kit needs

    How a view is pushed with the tab bar kept, the list-row and toggle widgets, the keyboard, toast and confirm dialog, and the library rescan call. NickelMenu, NickelDBus and NickelHardcover show where to start.

  4. Write a symbol table per firmware

    Every Kobo function the mod uses goes into symbols-4.38.23828.md with its signature. At startup the mod checks they all exist. If any is missing, the drawer disables itself and the menu fallback takes over.

  5. Re-check on each firmware update

    Diff the new libnickel against the table in Ghidra and update only what moved.

Reverse engineering here is for interoperability on a device you own, which is how NickelMenu and every other mod in the table below was made. Kobo's code stays on your Mac; we publish only our own code and the list of symbol names.

Risks

What could go wrong, and the guard for each

Boot loop from a bad mod

NickelHook's failsafe uninstalls a mod that crashes Nickel during startup. The mod's init stays tiny, and every new build is tested on your device in Phase 2 before features are added. Last resort: Kobo's own factory reset. Your books on USB storage are unaffected.

Firmware update changes libnickel

The startup symbol check catches it and the drawer turns off cleanly. Tools keep working through the NickelMenu fallback until I update the symbol table, usually a few hours of Ghidra diffing. Turning off Kobo auto-update avoids surprises.

Old Qt and an ancient compiler

Nickel runs an old Qt 5 and NickelTC uses an old GCC. NickelHook advises against the C++ standard library, so the kit uses plain Qt only.

Battery and storage safety

The mod lives inside Nickel all the time, even during USB sessions. It sleeps until opened, never holds files open on /mnt/onboard, and runs backends only while their screen is open or a sync is running.

Apps run with full device access

Backends run as root. Install only apps you or I wrote, or ones whose code you have read. A shared catalog waits until there is a way to trust apps.

Needed from you

Four answers to start

  • Okay to install Ghidra on your Mac

    Needs Java 21 and Ghidra. Each step is listed in docs/GHIDRA.md.

  • Okay to run a test mod on the Kobo

    Phase 2 loads a hello-world mod into Nickel. If it fails, the failsafe removes it. This is the first step with any boot-loop risk.

  • GitHub repo and folder

    Repo as owner/repo and the books folder. You'll paste the read-only token into a file on the Kobo yourself.

  • Turn off Kobo auto-update?

    Recommended while the drawer is young, so a firmware update never arrives before the symbol table is ready.
